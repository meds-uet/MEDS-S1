# M-07 — CoreMark & Dhrystone Benchmark Harness

## 1. Overview

M-07 implements a benchmark harness for evaluating RISC-V processor performance using two standard CPU benchmarks:

- CoreMark
- Dhrystone 2.1

The implementation provides:

- RISC-V bare-metal startup
- Minimal newlib system-call support
- RISC-V `mcycle` based timing
- CoreMark integration and validation
- Dhrystone 2.1 integration and validation
- Machine-readable result parsing
- CI-oriented benchmark execution
- Performance regression detection
- Benchmark result history

The current implementation uses a temporary Spike-based RISC-V environment because the final MEDS-S1 BSP/platform is not yet available.

The benchmark harness is structured so that the platform-specific layer can later be adapted to the actual MEDS-S1 BSP while keeping the benchmark and result-processing logic largely unchanged.

---

# 2. Objectives

The objectives of M-07 are:

1. Port CoreMark to the RISC-V target environment.
2. Port Dhrystone 2.1 to the RISC-V target environment.
3. Provide a reusable bare-metal startup environment.
4. Provide the minimum system calls required by newlib.
5. Measure benchmark execution using the RISC-V `mcycle` CSR.
6. Validate benchmark correctness.
7. Parse benchmark output into machine-readable results.
8. Automate benchmark execution through a CI-oriented runner.
9. Detect performance regressions greater than 3%.
10. Maintain benchmark result history.
11. Prepare the benchmark harness for final MEDS-S1 BSP integration.


The purpose of this platform is to provide the minimum environment required to execute the benchmarks without an operating system.

The temporary platform provides:

- Stack initialization

- BSS initialization
- C runtime initialization
- Basic output
- Basic newlib system calls
- Heap support
- Program termination

---

## 6.1 `crt0.S`

The `crt0.S` startup file performs the initial processor setup before the C program starts.

Its responsibilities include:

1. Initializing the stack pointer.
2. Initializing the global pointer.
3. Clearing the BSS section.
4. Calling the C runtime initialization.
5. Calling `main`.
6. Calling `_exit` after `main` returns.
7. Entering a safety loop after program termination.

The temporary stack top is:

```text
0x01010000
```

The startup code is shared between the M-07 benchmarks.

---

## 6.2 `syscalls.c`

The shared `syscalls.c` file provides the minimum system-call functionality required by newlib.

Implemented functions include:

```text
_write
_close
_fstat
_isatty
_lseek
_sbrk
_exit
```

### UART

Benchmark output is written to the Spike UART at:

```text
0x10000000
```

The `_write()` implementation sends characters directly to this address.

### Heap

The `_sbrk()` implementation provides a simple heap starting from `_end`.

Heap growth is limited so that it does not grow into the temporary stack region.

### Program Exit

The `_exit()` implementation reports the exit status through the RISC-V `tohost` mechanism and then enters a safety loop.

## 7.1 CoreMark Timing

CoreMark timing uses the RISC-V `mcycle` CSR.

The cycle counter is read using:

```c
static inline uint64_t riscv_read_cycle(void)
{
    uint64_t value;
    asm volatile ("csrr %0, mcycle" : "=r"(value));
    return value;
}
```

The benchmark records the cycle counter before and after the measured execution.

The difference represents the number of processor cycles consumed by the benchmark.

# 9. Timing Methodology

## 9.1 Why `mcycle`?

The RISC-V `mcycle` CSR provides a direct processor cycle count.

Using `mcycle` allows the benchmark harness to measure execution without assuming a particular processor frequency.

This is useful while the final MEDS-S1 clock configuration is not yet available.

# 12. Regression Gate

The regression gate is implemented in:

```text
sw/apps/regression_gate.py
```

The configured threshold is:

```text
3%
```

A result is blocked when:

```text
regression > 3%
```

Exactly:

```text
3.00%
```

is not blocked.

---

## 12.1 Baseline Selection

The regression gate searches for the latest accepted result for the same:

```text
benchmark
configuration
```

An accepted history entry contains:

```json
"accepted": true
```

A blocked entry contains:

```json
"accepted": false
```

Blocked entries are retained in history but are not used as future baselines.

---

## 12.2 Regression Calculation

The general calculation is:

```text
Regression % =
((Current Metric - Baseline Metric) / Baseline Metric) × 100
```

CoreMark compares:

```text
ticks per iteration
```

Dhrystone compares:

```text
cycles per run
```

A positive value indicates an increase in execution cycles relative to the baseline.

A value greater than 3% causes the regression gate to fail.

---

## 12.3 First Run Behavior

If no accepted baseline exists for a benchmark/configuration pair, the result is treated as:

```text
baseline
```

The first result is not blocked because there is no previous accepted result to compare against.
